跨机器同步 dsh 会话归档：dsh-archive-replica 插件的设计与踩坑

刘训臣

九月 12, 2026

背景：一个每天都在重复的小麻烦

实验室现在有几台机器都在跑 dsh（DeepSeek Harness）——办公室的台式机、笔记本、还有一台常开的服务器。会话日志本身是共享的：把 ~/.dsh/sessions 指向网盘目录（我们用坚果云）之后，每台机器都能看到全部会话，接着昨天没做完的对话继续干，这一点非常舒服。

但"归档“不行。某天我在 A 机把一批做完的项目会话归档，切到 B 机一看，它们又都躺在列表里——只能在 B 机再归档一遍。机器越多，这个动作重复得越多。

根因：归档状态不在会话日志里

翻了 dsh 的源码和数据结构后，问题很清楚：

数据存放位置会随会话目录同步吗
会话内容$DSH_HOME/sessions/<工作区>/<会话 id>/session.v3.jsonl.zstd✅ 会（我们已软链到网盘）
归档集合$DSH_HOME/storages/workspace.json 的 global.archivedSessionIds❌ 不会，本机文件

workspace.json 是 dsh 的 workspace 注册表：归档状态只是其中一个全局字段——一个 session id 的集合。它的写路径是"同目录临时文件 + rename"的原子替换，单写者、last-write-wins；而且归档是单向的（注册表只提供 archiveSession，没有取消归档）。

所以 A 机点归档，改的只是 A 机的 workspace.json，没有任何可同步的文件变化。

设计：每台机器各写一份文档

最直接的思路是"把归档集合写到一个共享文件里，大家读同一个文件”。但共享单文件在网盘上会立刻遇到两个问题：多端并发写会生成冲突副本（“两份都合法”），以及整文件覆盖会丢掉别人新加的 id。

最后采用的方案是每台机器只写自己的文档：

共享目录/（交给任意网盘同步：坚果云 / Dropbox / iCloud / Syncthing…）
├── archive-desktop.json      ← 办公机写
├── archive-laptop.json       ← 笔记本写
├── archive-server.json       ← 服务器写
├── unarchived-desktop.json   ← 撤销清单（只有撤销过才出现）
└── …
  • 读取时对所有 archive-*.json 取并集 —— 每台机器看到的就是全量归档集合；
  • 每台机器一个文件 ⇒ 永远只有一个写者，结构上不可能出现冲突副本；
  • 并集只增不减，撤销靠独立的撤销清单跨机器传播（否则下一次并集会把撤销过的 id 又播回来）；
  • 各机文档会自然收敛到同一个并集，任何一台机器的文件都能独立恢复整套归档。

插件本体装在 $DSH_HOME/plugins/archive-replica，通过 profile 的 patch 层用一行 insert 挂载。这样做的好处是：替换整个 dsh 源码目录（升级）也不会丢插件，而且不需要改 dsh 源码——毕竟我们只是给自己用的工具，不该去动上游仓库。

实现里的几个关键决定

① 只调用注册表 API，绝不自己写文件。 归档动作走 dsh 进程内的 ctx.workspaceRegistry.archiveSession()，由注册表自己串行落盘。这样既没有并发覆盖风险，也不需要像早期脚本版那样"抓 token → 换 cookie → 发 RPC"。

② 轮询，而不是文件系统监听。 网盘客户端的 inotify 通知本来就不可靠（文件可能是云端推送来的，本机没有任何写事件）；另外外置插件解析不到第三方依赖（早期用 chokidar 的版本在启动时直接报 Cannot find package），于是目录发现改为内建轮询，默认 2 秒一次。

③ 机器指纹。 每台机器写文档时附带一个指纹（短主机名 + 内核 machine-id 前 12 位）。如果共享目录里出现了同名但指纹不同的文档，说明两台机器撞了 machineId，安装脚本会直接拒绝安装——hostname 重复在实验室里太常见了（我们就有两台都叫 fedora）。

④ 撤销是全局语义。 上游没有 unarchiveSession，撤销只能先停 dsh（它内存里的注册表才是权威），再由脚本改写注册表并清理所有同步落点，同时写一份本机撤销清单；另一台机器跑同一条命令（不带参数）就会应用该清单。一台撤销，所有机器都不再归档它。

安装与使用

npm 一条命令装好（需要 dsh 的 harness home，默认 ~/.dsh）：

npm i -g dsh-archive-replica
dsh-archive-replica-install --enable --vault "<共享目录>" --machine "<本机唯一 id>"
# 然后重启 dsh

配置项很少：

字段必填默认说明
directory✅无共享目录的绝对路径
machineId短 hostname每台机器必须不同，匹配 [A-Za-z0-9._-]{1,64}
pollIntervalMs2000轮询周期（毫秒）

前置条件只有一个：会话日志本身要能跨机器（也就是把 ~/.dsh/sessions 软链到网盘目录）。插件跨机器传的只是"归档 id"，不传日志。

一路踩过的坑

这部分大概是本文最有价值的内容——每个坑都真实地把我们绊倒过。

坑 1：不要把 workspace.json（或 storages/）软链进网盘

很自然的想法是"既然归档状态在这个文件里，那把整个 storages/ 软链到网盘不就行了"。我们试过，不行：

  • dsh 的写路径是"同目录临时文件 + rename 覆盖目标"，而 rename 会把软链本身替换成普通文件——第一次归档之后同步就悄悄断了；
  • 即使软链整个目录，整文件 last-write-wins 也会让两台机器互相整份覆盖（工作区记账、排序都在同一个文件里），网盘还会不停生成冲突副本。

坑 2：npm 打包会剥掉非 bin 文件的执行位

插件用一个无扩展名的 bin shim 暴露安装器（npm 会静默移除以 .sh 为目标的 bin），shim 内部转发到包里的 install.sh。从 git clone 用一切正常，但 npm i -g 之后运行必然报：

Permission denied: .../dsh-archive-replica/bin/../install.sh

原因是 npm 打包时只给 bin 里的文件保留执行位，install.sh 装出来是 0644，直接 exec 当然失败。修法是 shim 里显式用解释器调用：exec bash "$(dirname "$self")/../install.sh" "$@"。

坑 3：纯数字的 machineId 会让 dsh 起不来

我们的机器 id 有的用型号，有的用编号（1234 这种）。安装器把它写进 YAML：

machineId: 1234      # YAML 会解析成数字

而插件 schema 要求字符串，于是 dsh 启动时整棵插件树加载失败：

Error: dsh: plugin tree failed to load: failed to apply loader entry archive-replica-external
  (@local/dsh-archive-replica): invalid config:
  - $.machineId expected string but got 1234 (at machineId)

一个引号的事，代价是 dsh 完全起不来。现在安装器生成的 YAML 一律给值加单引号并转义（machineId: '1234'）。

坑 4：两套同步机制并存，会互相"回灌"

早期版本是一个外部脚本（启动包装 + 运行期同步 + 离线合并），后来才改成插件。过渡期两套同时存在，各有各的同步文件。结果一次误归档的恢复失败了：改完注册表一重启，退役脚本版的"启动前离线合并"又把归档灌了回来。教训：撤销必须把所有落点一次清干净，漏一处就会被下一轮合并/扫描带回来。

现状

  • 三台机器都已接入，共享目录里的并集自动收敛；任意一台归档/撤销，其余机器在一个轮询周期内跟随；
  • 代码与文档：https://github.com/liuxunchen/dsh-archive-replica（docs/cross-machine-sync.zh.md 是完整的原理、安装与排障说明）；
  • npm：https://www.npmjs.com/package/dsh-archive-replica（npm i -g dsh-archive-replica）。

小结

这个插件的技术含量不高，但把三件事想清楚之后就很稳：谁是单写者（一台机器一个文件）、什么该进日志什么该进派生文件（撤销用清单而不是删 id）、以及同步工具的语义边界（rename 会吃掉软链、整文件覆盖会互相打架）。如果课题组里也有人同时在多台机器上用 dsh，装上这个插件应该能省掉每天那几次重复的归档操作。
